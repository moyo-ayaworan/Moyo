# Repository security audit — 13 November 2026

This is a repository-wide security review of the current first-party code, with fixes for confirmed defects. It extends the earlier payment audit in [payments-security-review.md](payments-security-review.md).

A fresh [cross-path security follow-up](security-audit-follow-up.md) adds five further fixes and explicitly documents the remaining session, trial-abuse, capacity and infrastructure limitations. Latest automated test total: **128 passed**.

## Coverage and method

The source inventory covers approximately 34,503 lines in 289 files: application routes and pages, components, contexts, libraries, SQL schemas, scripts, tests, public SVGs and deployment configuration. Exact paths, hashes and methods are recorded in `output/code-audit-coverage.json`; reproducible scan evidence is in `output/code-audit-static.json`. Run `node scripts/audit-source.mjs` to refresh the static inventory.

Every inventoried file was scanned. TypeScript/JavaScript was parsed into an AST, client import paths were checked for server dependencies, and sensitive sinks were examined: SQL construction, network requests, raw HTML, filesystem access, navigation, browser storage and credential literals. Authentication, authorization, private media, public API inputs, financial state changes, desktop activation and account/review boundaries received focused manual review. Earlier payment review and sandbox acceptance evidence remain relevant.

**This is not a claim that every line was manually read or that no undiscovered vulnerabilities exist.** Static coverage and focused manual coverage are distinguished in the manifest. Dependencies are assessed using npm advisories rather than individually reviewing vendor source. Generated output, environment values, binary media/installers, external desktop source, git history and deployed account/provider settings are outside this source inventory.

## Findings fixed

| ID | Severity | Evidence and impact | Fix |
| --- | --- | --- | --- |
| A1 | Medium | `gallery_documents.gallery_id` cascades on gallery deletion. The gallery DELETE route bypassed the document DELETE route's paid-record protection, allowing an authenticated administrator to inadvertently erase manually paid invoices/history. Online payment foreign keys protected some, but not all, records. | `app/api/galleries/route.ts:303`: lock the parent gallery before checking its documents; refuse deletion of any gallery containing documents. Existing financial records remain intact. |
| A2 | Medium | `SessionTracker` sent arbitrary pathnames to `/api/notify-session`, which emailed and logged them. Booking/collector bearer tokens appear in pathnames, extending private-link exposure to mail and log retention. | `lib/privacy.ts:9`, `components/SessionTracker.tsx:12`, `app/api/notify-session/route.ts:19`: allow only exact public paths on both client and server. Direct submissions of private paths receive 204 without email. Inquiry logging also stops recording client names/emails in routine send logs. |
| A3 | Medium | Gallery review and selection approval validated access codes without using the rate limiter protecting the main access route, providing alternate code-guessing endpoints. | Both endpoints share the `gallery-access` attempt budget, validate positive integer IDs and bound request bodies. |
| A4 | Medium | A paid-receipt worker could mark an outbox entry sent after refund/dispute processing had requeued the same entry, suppressing the newer customer/studio review notification. Download authorization separately rechecks payment status, so this did not itself grant refunded downloads. | `lib/payments/notifications.ts:20`: acknowledge delivery inside a transaction after locking/rechecking the current order, using the same order-before-notification lock ordering as financial updates. A stale worker cannot acknowledge the newer status. |
| A5 | Low | Several public JSON endpoints checked only Content-Length, or validated size after fully reading the body. Missing or inaccurate Content-Length bypassed the application-level memory limit. Hosting request limits partially mitigate this in production. | `lib/requestBody.ts`: count actual streamed bytes and cancel oversized requests before parsing. Applied to chat, tracking/contact email, gallery access/review/selection, subscription, beta signup, booking creation/recovery and art inquiry creation. Newsletter input is also bounded. |
| A6 | Low | The chat privacy filter caught booking links but missed collector/review links, access fragments and unlabelled Paystack credentials. Pasting them could send them to the AI provider. | `lib/privacy.ts:13`: check these formats, including URI-encoded private paths, before provider requests and when scrubbing history. This remains a heuristic, not a guarantee of detecting arbitrary personal information. |
| A7 | Low | The authenticated newsletter's regex sanitizer allowed unwanted HTML and obfuscated URL schemes. Recipient mail clients may block active content, but the server was not enforcing the intended HTML boundary. | Replace it with a maintained parser-based `sanitize-html` allowlist; preserve basic formatting and HTTP(S)/mailto links. External paste inserts plain text; link creation validates schemes; dropped markup is rejected. |
| A8 | Low | Cron signature guards compared JavaScript string length before comparing UTF-8 buffers. Equal character counts with different byte counts could throw instead of returning an authorization failure. Malformed authenticated-media URI encoding could also throw during parsing. | Compare byte lengths in both cron handlers; malformed media URLs now return null. Regression coverage includes a multibyte Authorization value. |
| A9 | Low | Private pages inherited general indexing/referrer behavior; local browser snapshots and verification outputs were not excluded from git. | Add noindex/noarchive, no-referrer and private/no-store headers to private page paths, and git-ignore generated verification/browser artifacts. |
| A10 | Medium | Newsletter signup immediately activated supplied addresses and reactivated withdrawn subscriptions without mailbox proof; no unsubscribe endpoint/link existed. | New signups stay pending. Hashed, expiring, single-use confirmation tokens require an explicit same-origin POST. Reactivation also requires proof. Personalized campaign messages contain list-scoped unsubscribe links; withdrawal invalidates pending confirmation links. Recipients never receive another subscriber's token. Existing active subscriptions are preserved. |

## Boundaries checked without a new confirmed bypass

- Admin session cookies are signed, expiring, HttpOnly and SameSite Strict. API handlers enforce server-side administrator checks; the proxy is additional protection, not the sole API boundary.
- SQL values are parameterized. Dynamic SQL fragments reviewed are fixed allowlists, static schema strings, parameter placeholders or validated disposable schema names.
- Account review ownership, device bearer tokens, single-use pairing, review-code hashing/encryption, publication state, viewer scope, expiry, JPEG decoding/reencoding and quotas are enforced server-side.
- Payment amounts/currency/environment/buyer/reference/metadata are checked against server-owned orders. Webhook signatures, durable fulfillment, provider uniqueness, pending checkout reuse, refund/dispute locks and final-delivery settlement checks are covered by the focused payment review and tests.
- Digital delivery uses private authenticated media and signed buyer access. Public shop/product responses omit delivery file URLs. Photography and fine-art collections remain separate; MELATONE remains NGN 20,000.
- The scan found no server-only import path in the inspected client import graph, no matching live secret/private-key literal in inventoried source, no active SVG content, and no TypeScript/JavaScript parse errors. These are bounded scan results, not exhaustive secret detection or runtime proofs.

## Open findings and verification limits

1. **Legacy newsletter records:** existing active subscriptions were preserved rather than silently removed or contacted. Historical mailbox ownership cannot be established from the stored records. New signup/reactivation now requires confirmation. Campaign delivery remains synchronous with three bounded workers and provider-acceptance checks; it is not a durable campaign queue and cannot guarantee mailbox delivery or exactly-once resend after an uncertain transport failure. No real campaign or confirmation email was sent during this audit.
2. **Development override maintenance:** remove the narrowly scoped minimatch override when TypeScript ESLint adopts a patched dependency range. The original advisory was [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249); the final full npm audit is clean.
3. **Low — operational growth:** general rate-limit rows and some licensing challenge/event history require a retention policy as traffic grows. Per-client limits do not prevent a distributed attacker from exhausting aggregate database/provider capacity. The code assumes the deployment overwrites the trusted client-IP header; verify this if moving away from Vercel.
4. Frontend cleanup additionally passed browser checks for password-reset URL initialization and forward/backward private book navigation using synthetic data and mocked APIs. It does not constitute a live purchase or real account change.
5. Production database grants/public data APIs, backup/restore, secret strength/rotation history, provider account permissions, DNS/TLS custom-domain configuration and external desktop enforcement cannot be certified from this repository. No broad production-secret download or privileged configuration mutation was performed for this audit.
6. Per your instruction, **no live payment or refund was made**. Prior genuine Paystack TEST-mode checkout/settlement/receipt/private-delivery/licensing checks are documented in the payment report. Live settlement and actual recipient mailbox delivery remain untested.
